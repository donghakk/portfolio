  • 기간 / 인원: 2026.05 ~ 현재 / 1인 (단독 설계·구현·운영)
  • 기술 환경: Node.js 20 (ESM), Playwright, Google Sheets API, Google Apps Script, Cloudflare Workers, Docker, AWS CDK·ECS Fargate·EFS·Secrets Manager·EventBridge
  • 아키텍처 수집(2단계 파이프라인) → 규칙 기반 분류 → 검토 큐(사람 판단) → 발송(검증 게이트 · 일일 한도 · 라운드로빈) → 수신거부 처리 └ 데이터 저장소: 스프레드시트(SSOT) — 현업이 직접 열어 수정
  • My Role & Contribution
  • "DB를 넣지 않는다"는 설계 결정 — 현업 담당자가 결과를 직접 열어 수정해야 하는 업무 흐름을 반영해, 기술적 정석 대신 스프레드시트를 단일 데이터 기준(SSOT)으로 채택. 별도 관리 화면 없이 운영 가능한 구조 확보
  • 규칙 기반 3-state 분류기 설계 — 신호별 기여도를 실측해 약한 신호 5개를 제거한 린(lean) 분류기로 개선. 판단이 애매한 건은 자동 분류하지 않고 검토 큐로 라우팅해 사람이 결정(Human-in-the-loop). → 정밀도 100% / 재현율 81% / F1 89% (재크롤 66건 검증, 오분류 0건)
  • 시스템 경계의 신뢰성 확보 — 수신거부 토큰(HMAC-SHA256)이 Node.js와 Apps Script 두 런타임에서 동일하게 생성되어야 기존 발송분의 링크가 유효한 구조. 양쪽 토큰을 대조 검증하는 절차를 만들어 런북화
  • 운영 안전장치 — 일일 한도를 매 처리마다 즉시 디스크에 flush(크래시 시에도 한도 초과 방지), 발송 직전 검증 게이트(변수 미치환·필수 안내 누락 시 발송 거부), 연속 실패 3회 시 계정 자동 중단, dry-run 기본값
  • 트러블슈팅 (사후분석 문서 3건)
  • 동시성 Race Condition — 수집 데이터가 행 단위로 뒤섞이는 오기입 발생. 처음엔 '중복 수집'으로 오진했으나, 재검증 끝에 Playwright page 인스턴스를 태스크 간 공유해 생긴 경합임을 규명 → task-scope page로 전환해 해결
  • 봇 차단 대응 — 8시간 이상 실행 중 강제 중단. 발견 즉시 JSONL 체크포인트로 flush해 중단에도 데이터 보존, 실행 간 dedupe, jitter throttle 도입. "동시성 N배 = 시간 1/N이지만 단일 IP 동시요청이 차단의 핵심 원인"임을 정리해 옵션 4개를 비교한 제안서를 쓰고 보수적 도입 권고
  • API 쿼터 초과 — 쿼터 리셋 기준이 PT(태평양시)인데 KST로 계산한 본인의 실수. 원인과 재발 방지책을 문서화
  • 클라우드 이관 & 최소권한 설계 — 개인 노트북 절전으로 실행이 중단되는 구조적 리스크를 해소하기 위해 AWS Fargate 이관 추진. 1차안(CDK)이 cdk bootstrap의 admin 권한 요구로 보안상 반려되자, CDK 없이·admin 없이 배포하도록 재설계하고 요청 권한을 ECS 실행 역할 1개 + 리소스 한정 PassRole로 축소. 시크릿 접근도 단일 ARN으로 제한하고 수동 배포 런북 작성
  • 규모: 약 9,000 LOC / 설계·트러블슈팅 문서 21건
